# 接受字符级 OT 承载结构化块清单的天花板

块清单是一份 JSON，跑在按字符收敛的 OT 之上。OT 保证两端最终得到同一份文本，但它不知道这份文本是 JSON，因此并发写入可以收敛到一个语法合法却语义损坏的结果。我们接受这个天花板，只做最小差异传输加损坏防护，不重建同步层。

## 实测数据

用仓库自己的 wasm OT 实现跑并发场景，对比两种操作构造方式：

| 场景                            | 全量替换（删全文 + 插全文） | 公共前后缀最小差异                               |
| ------------------------------- | --------------------------- | ------------------------------------------------ |
| 改 2224 字节清单里的一个高度值  | 每次传 2718 字节            | 每次传 17 字节                                   |
| 两端改不同块                    | 两份 JSON 拼接，解析失败    | 正确合并                                         |
| 两端各加一个块                  | 两份 JSON 拼接，解析失败    | 正确合并                                         |
| 两端改同一个高度值（420 / 500） | 解析失败                    | 得到 4250，解析通过但值无意义                    |
| 一端删块、一端改同一块标题      | 解析失败                    | 块 id 变成 `XYZccc`，解析通过但语义损坏          |
| 两端同时拖拽排序                | 解析失败                    | 3 块变 5 块，id 重复，解析通过但语义损坏         |
| 两端同时给空文档播种            | 解析失败                    | **仍然解析失败**（无公共前后缀，退化为全量替换） |

最小差异消除**语法**损坏，消除不了**语义**损坏。

## 被否决的方案

**改成一行一个块的 JSONL 格式。**
直觉上「一块一行」能让 OT 的行为对齐块的边界，实测不成立：同样的语义损坏照样出现——两端改同一块时行内字符仍然交错，两端排序时行仍然重复。换序列化格式救不了这个问题，根因是字符级 OT 不理解结构，而不是 JSON 这个具体格式。

**重建为结构感知的同步层**（CRDT 或按字段分文档）。能真正解决问题，但改动量与风险远超收益：唯一一个不需要人操作就会发生的并发场景只有一个（见下），其余场景需要两个人同时对同一页面做结构修改，在本项目的单人多设备使用场景里概率接近零。

## 决策

1. 块清单的同步改用公共前后缀最小差异，与 Monaco
   OT 客户端共用同一份算法。这消除全部语法损坏场景中除播种以外的部分，并把一次布局改动的写入量从整份清单降到几十字节。
2. 针对「两端同时给空文档播种」——唯一一个不需要人操作就会发生的并发场景——做播种自愈：客户端播种后若收到的服务端内容解析失败，用最近一次有效清单重写服务端。
3. 解析后做结构校验：剔除 id 不符合生成规则的条目、去除重复 id。这让语义损坏以「块消失」而不是「块看起来正常但其实是坏的」的形式表现出来。
4. 人为的并发结构修改不做防护。

## 推翻这个决策的条件

出现真实的多人并发结构修改场景——同一页面上两个人同时增删块或调整块顺序，且不是同一个人的两台设备。可观察信号：用户报告块莫名消失或重复，且日志显示两个不同来源在秒级内先后写入同一份块清单。届时应重建为结构感知的同步层，而不是继续给字符级 OT 打补丁。
