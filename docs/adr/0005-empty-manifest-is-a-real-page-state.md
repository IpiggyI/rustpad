# 空块清单是一种真实页面状态，不是未初始化

`useManifest`
原本把"服务端清单解析出零个块"当成"服务端没有可用清单"，然后从本地快照或默认清单播种一个块。这条判断让"删到零块"这个状态无法保存：刷新一次，块就自己长回来了。

我们把判断依据从"块数组是否为空"换成"权威原文是否为空"。有效清单一律采用，包括
`blocks: []`；只有首轮完整历史回放结束、且权威原文确实是空字符串时，才走播种分支。非空但解析失败的文本按损坏处理，不能当作新页面覆盖掉。

## 决策依据

零块清单和新页面是两种不同的事实，原先被同一个条件吞掉了。原文为空能区分它们：真正没人写过的页面，服务端文档就是空的；删到零块的页面，服务端文档是一段合法的
`{"version":1,"blocks":[]}`。

顺序守卫是这条判断能成立的前提。`onContentChanged` 同样会调用 `useManifest` 的
`initialize()`，而 `RustpadHeadless.applyOperation()`
在历史回放中是逐笔通知的，所以中途会出现"暂时还没有块"的瞬间。首轮完整历史回放结束之前，不初始化、不迁移、不播种；`RustpadHeadless.markContentReady()`
是这个"首轮回放已结束"的一次性信号。

同一个守卫也服务于块高度的一次性迁移。迁移标记写在清单根上（新字段，不借用
`version`），因为它描述的是整个页面，零块页面也要能表达"已迁移"；逐块标记做不到，设备本地的键约束不了第二台设备。`sanitizeManifest()`
只重建 blocks 数组并展开根对象，所以根字段能活过一次解析和序列化；但
`initialManifest` 的构造、快照保存和 `useManifest`
的初始状态都在重新挑选根字段，标记必须贯穿这三处。

## 后果

- 新页面第一次打开时，服务端原文为空，行为不变：有快照用快照，没有就播种一个默认块。
- 删到零块的页面刷新后仍然是零块，第二台设备打开也是零块，界面必须提供新增入口。
- **并发迁移不保证严格只执行一次。** 服务端 `apply_edit()`
  会变换过期版本的操作，不会拒绝它（见
  [字符级 OT 决策](0002-character-ot-for-structured-manifest.md)）。两台设备同时首次打开同一个未迁移页面时，迁移可能提交两次。两次都把高度写成同一个值，所以结果相同；但这不是靠协议保证的。
- **服务端清理会抹掉这项区分。**
  默认配置没有数据库（`rustpad-server/src/lib.rs:82`），清理器会移除超过保留期未访问的文档（`rustpad-server/src/lib.rs:196`）。文档被清理后，旧页面和新页面同样返回空原文，本地旧快照可能复活已删除的块，也可能让高度迁移重跑一次。加根字段解决不了这个问题，它随文档一起消失。

## 推翻这个决策的条件

服务端改为按版本条件提交清单写入，能拒绝过期的结构性修改。那时迁移与删除都可以要求严格一次，客户端守卫不再是唯一防线。另一种情况是块清单不再走字符级 OT，改用服务端认得的结构化操作，"原文为空"这个信号本身就没有了。
