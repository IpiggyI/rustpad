# 图片存放在服务端磁盘目录，正文只保存相对地址的图片引用

粘贴或选择的图片先上传到服务端，保存在环境变量 `IMAGE_DIR`
指定的磁盘目录里。协同文档正文只插入一段 markdown 图片引用，地址是相对路径
`api/images/<图片id>.<扩展名>`。图片属于整个服务端，不属于某个页面或块。上传相同字节时复用已有地址；没有引用的图片保留 30 天后回收。

服务端启动时扫描一次数据库和内存中的协同文档，此后每小时扫描。图片第一次被确认没有引用时开始计时，重新上传或恢复引用后重新保护。计时记录保存在图片目录的
`.image-state.json`
中，重启后继续使用。升级前的图片从首次扫描开始计时，不根据文件名日期直接删除。

块清单已明确移除的块，其旧正文不再保留图片。其他协同文档仍引用同一图片时继续保留。块清单缺失、格式不完整或数据库与内存中的块清单有分歧时，保守保留对应引用。读取文档、扫描目录或保存清理状态失败时停止当轮删除。上传、正文编辑与清理共享同步控制；操作系统文件锁限制同一目录同时只能由一个服务进程修改。

## 考虑过的方案

- **把图片转成 base64 写进正文。** 服务端拒绝目标长度超过 256 KiB 的编辑（`rustpad-server/src/rustpad.rs`
  的 `apply_edit`），一张普通截图转码后就可能超限。新客户端连接时还会收到完整的操作历史，图片数据会在每次连接时重复下发。
- **存进 SQLite 表。** 持久化是可选的，只有设置了 `SQLITE_URI`
  才有数据库；没有数据库时图片无处可存。图片还会让数据库文件快速变大，备份和恢复都变慢。
- **地址里带页面 id。** 项目没有登录，按页面划分挡不住任何人访问；服务端也没有删除页面的接口，按页面归属带不来"随页面一起删除"的好处，只会让地址变长。
- **写完整地址（带主机名或 IP）。** 内网主机的 IP 可能变化，变化后所有旧引用失效。相对路径与
  `src/useHash.ts` 拼 socket 地址的方式一致，也能在子路径部署下工作。

## 后果

- 把正文复制到 Rustpad 以外的地方，图片引用会失效，因为相对路径离开了服务端就无法解析。
- 正文删掉图片引用后，图片进入 30 天保留期；上传后没有插入正文的图片和进程中断留下的上传临时文件也会回收。
- 字节不同但画面相同的图片不会合并。已有重复文件继续保留各自的有效地址，直到不再被引用并达到清理期限。
- 浏览器缓存、导出的正文和撤销历史不是保留依据。超过保留期后恢复这些内容，原图片地址可能失效，需要重新上传。
- 未配置数据库时，服务端重启或内存文档过期后，图片引用也随文档消失；图片随后按同一期限回收。
- 备份必须同时复制数据库文件和图片目录，只复制其中一份会丢图片或丢引用。
- 不设置 `IMAGE_DIR` 时，服务端不接受上传，这与 `SQLITE_URI` 不设置就不持久化的做法一致。

## 推翻这个决策的条件

需要按页面控制访问（加入登录或访问口令），或者需要多个服务进程共享图片目录。前者要求地址带上归属信息，后者要求跨进程协调文档引用与回收。
