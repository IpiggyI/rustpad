# 09：调查单文档模式隔夜重开后的折叠丢失

**What to build:**
建立从关闭前保存到重新打开后恢复的可观察诊断过程，解释同一设备隔夜重开时偶发全部展开的原因，为后续修复提供可验证的因果证据。本票交付诊断，不预设修复位置。

**Blocked by:**
08：验收分块展示与 Markdown 回车的组合行为。此边为用户指定的执行顺序，要求先完成功能开发与验收，再开始问题诊断；它不是功能依赖。

**Status:** ready-for-agent

- [ ] 核对现有修复和验证记录，保留用户报告的现场边界：单文档模式、同一设备、关闭后约一晚上重开、暂不能稳定复现。
- [ ] 核实可访问的实际运行环境，包括浏览器版本、服务实例、数据库是否启用、过期配置和重启记录；无法访问的环境明确标为未验证，不用仓库默认配置代替实际配置。
- [ ] 对照关闭前读到的折叠、最后一次写入、本地缓存、服务端旁路协同文档和重新打开后采用的记录，区分记录丢失、被覆盖和恢复失败。
- [ ] 检查正文加载、语言确定和折叠范围计算的时序；保存记录正确但恢复失败时，证据能指出失败发生在哪个阶段。
- [ ] 按已有证据选择关闭重开、延迟加载或服务重启等可控场景；诊断只采集必要状态、时序和折叠范围，不记录正文或凭据。
- [ ] 对确认的原因提供可重复失败场景，或能区分竞争解释的直接证据；不得仅凭静态风险认定根因，不追加推测性的产品修复。
- [ ] 形成可复查的诊断报告。若证据仍不足，明确标记根因未定位，记录已排除路径、缺失观测和下一次可执行探测；本轮调查记录不能代替根因确认或问题解决。
- [ ] 根因明确后，给出最小修复范围、可能受影响的共同调用路径和验证场景，作为补充修复票的依据。不要在本票中静默实施修复。
- [ ] 报告区分自动化因果证据与用户设备隔夜验证；未经用户报告，不宣称隔夜问题已解决。
