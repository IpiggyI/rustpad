## Comments

### 首轮结论（2026-09-15；后续进展见文末）

**根因未定位。**
本轮排除了四条路径，确认了两个真实缺陷，但没有复现用户报告的隔夜折叠丢失。下面记录已排除路径、已确认缺陷、缺失观测和下一次可执行探测。

### 已核实的运行环境（用户于 2026-09-15 提供）

部署命令的关键参数：`EXPIRY_DAYS=3600`、`SQLITE_URI=sqlite:///data/rustpad.sqlite3`、命名卷
`rustpad-data:/data`、`--restart unless-stopped`、`--user 1000:1000`、未发布端口。

实测输出：

```
docker inspect → restarts=0 started=2026-09-11T11:31:46Z
/api/stats     → {"start_time":1789126306,"num_documents":20,"database_size":77}
```

用户确认丢失发生在 2026-09-11 那次启动**之后**。

### 已排除的路径

1. **内存驱逐**。清理器的条件是未访问时长超过 `expiry_days`
   天（`rustpad-server/src/lib.rs:196-209`），配置为 3600 天，实际不会触发。
2. **持久化未生效**。`database_size`
   为 77，说明写盘在发生。另外服务端在打不开 SQLite 文件时直接 panic 退出（`rustpad-server/src/main.rs:22`），因此
   `restarts=0` 同时证明卷可写。
3. **容器重启导致文档消失**。`restarts=0`，且丢失发生在该次启动之后。结合第 1 条，服务端自 9 月 11 日起一直持有已访问文档，不可能丢掉折叠记录。
4. **重启后从 SQLite 读回时被客户端抢跑**。用
   `scripts/probe-folds-after-restart.mjs`
   在本地按相同配置（启用 SQLite）连做 5 轮：折叠 → 关闭页面 → 等待落盘 → 重启服务 → 同一浏览器上下文重开。5 轮全部保留折叠，旁路文档内容完整读回。

### 已确认的缺陷

见 [票 10](10-shared-document-late-seed-doubling.md)。折叠旁路文档 `folds:<id>`
存在迟到播种：两个客户端各自把 `{}` 写进去，文档一度变成
`{}{}`，再由某个客户端删掉重复的一半。同一缺陷也出现在块清单上，且早于本版工作（在
`40fb8c3` 上同样复现）。

这条与折叠丢失有机制上的联系：`applyFoldSidecarText`（`src/singleDocFolds.ts:254-277`）在首次初始化时采用任何可解析的旁路内容——包括
`{}`——并且**不与本地缓存合并**。刚被播种的旁路文档内容恰好就是
`{}`。翻倍窗口内内容为
`{}{}`，不是合法 JSON，解析失败后又转而采用本地记录。采纳哪一份取决于客户端在这段窗口里的到达时序。

**但机制成立不等于就是本次原因。**
本轮没有让这条路径真正丢掉折叠，因此不作为根因。

### 缺失的观测

最有价值的一条：**两次打开之间，该文档是否在别的设备上被打开过。**
折叠旁路文档按设计是跨设备共享的（见
[ADR 0003](../../../docs/adr/0003-single-doc-folds-in-sidecar-collab-doc.md)），任何一个客户端只要算出"当前没有折叠"，就可能把这份共享记录覆盖掉。如果那晚手机打开过同一个文档，这就是目前最合理的解释。

其次是出问题那台设备的浏览器与版本，以及本地存储是否仍在。

### 下一次可执行的探测

1. **第二客户端覆盖**：让一个客户端在恢复被扰动的情况下打开文档（正文尚未加载、或语言尚未确定），观察它是否把空折叠记录写进共享旁路文档。这是当前最高优先级。
2. **语言确定时序**：折叠记录按语言分键保存。若 `Language`
   消息晚于恢复尝试到达，查找会落空。延迟该消息，观察恢复与随后的写入。
3. **关闭路径写空**：`flushFoldMementoOnUnmount` 与 `commitSessionFolds`
   在编辑器已拆除时是否可能写入空记录。第 4 条探测里的正常关闭没有出现这种情况，但只覆盖了干净关闭。

### 恢复调查：编辑后折叠记录未更新（2026-09-20）

用户再次报告编辑后关闭重开会丢失折叠，并要求从实现原理排查。本轮已在真实浏览器中复现并定位一条原因：**正文编辑改变了折叠记录的位置或校验值，但没有触发保存。重开时，旧记录与新正文不匹配，Monaco 拒绝恢复。**

这是本机已验证的缺陷，尚未核对用户部署是否运行相同前端。`needs-info`
现在仅保留用户现场匹配待验证的边界；不再表示缺少第二设备信息就无法继续调查。本票交付诊断与修复范围，产品源码未修改。

#### 复现条件与最小场景

- 基线是 `f5ba6a7`，开始时工作区干净。浏览器实际加载的 Monaco 版本由探针断言为
  `0.52.2`。
- 本机 Vite 使用仓库当前源码，后端使用已有 `target/debug/rustpad-server`，端口为
  `3030`，`EXPIRY_DAYS=3600`。本轮未启用 SQLite，也不涉及重启、过期或磁盘恢复。后端二进制对应的提交未核对；本结论来自前端事件与运行中服务端记录的直接观察。
- 同一个浏览器上下文关闭页面后重开；无第二个编辑设备，无需隔夜等待。
- 最小正文是三行：`visible`、`## Folded`、`body`。折叠第二行，在第一行第一列真实按下回车，等待 1200 毫秒，再关闭页面。
- 关闭前额外核对服务端正文已经等于编辑器正文，避免把正文未同步混入折叠丢失。

| 时点           | 编辑器实时折叠记录 | 服务端折叠记录   | 可见结果      |
| -------------- | ------------------ | ---------------- | ------------- |
| 编辑前         | 第 2 至 3 行       | 第 2 至 3 行     | 第 3 行隐藏   |
| 前方插入一行后 | 第 3 至 4 行       | 仍是第 2 至 3 行 | 第 4 行仍隐藏 |
| 关闭后         | 编辑器已关闭       | 仍是第 2 至 3 行 | 无页面        |
| 重新打开后     | 没有折叠           | 仍是第 2 至 3 行 | 全部展开      |

插入一行期间的事件计数为：正文变化 1 次、折叠模型更新 1 次、公开隐藏区域变化 0 次。单文档折叠缓存写入 0 次，缓存也保持旧记录。此场景中没有其他设备写入，没有空数组覆盖，也没有服务端记录消失。

分块编辑器的同一场景同样失败：块清单中的折叠记录仍停留在旧行号。它不是仅影响单文档旁路存储的问题。

#### 因果验证与源码位置

1. 单文档只由 `src/SingleDocView.tsx:305` 的 `onDidChangeHiddenAreas`
   触发正常保存。分块的相同入口在
   `src/BlockEditor.tsx:285`。正文变化会通知正文协同层，但没有触发折叠保存。
2. Monaco 用跟随编辑移动的位置标记读取折叠起止行，并计算首、末隐藏行的校验值。见
   `node_modules/monaco-editor/esm/vs/editor/contrib/folding/browser/foldingModel.js:104-181`。所以用户没有点击折叠按钮，折叠记录仍可能变化。
3. Monaco 比较新的隐藏区间与已经随编辑移动的位置标记。如果两者相同，则不报告视图行映射变化。见
   `node_modules/monaco-editor/esm/vs/editor/common/viewModel/viewModelLines.js:75-90`。公开隐藏区域事件仅在该比较报告变化时发送，见同目录
   `viewModelImpl.js:366-399`。这与实测的事件计数一致。
4. 恢复时，Monaco 检查记录范围与校验值，不匹配就跳过该记录，见
   `foldingModel.js:154-176`。这解释了只展开的方向性：原记录还在，但已经不能用来恢复当前正文。
5. 对照实验仅在关闭前把服务端折叠记录更新为实时记录，保留正文和恢复实现。单文档与分块重开后都能恢复第 4 行隐藏。这个操作是探针中的因果干预，不是已实现的产品修复。

React 组件清理中的同步读取不能替代页面关闭保障。当前折叠保存没有注册页面退出事件；正文的
`beforeunload`
只检查正文待确认操作（`src/rustpad.ts:116-124`）。本轮页面关闭后的服务端记录实测仍为旧值。不能把过去“组件卸载会刷新记录”的单元测试推广成“关闭标签页会保存”。

#### 建议的修复范围

保留现有跨设备语义和存储格式，先修复单文档与分块共同的折叠采集机制：

- 把正文变化、折叠模型重新计算和主动折叠操作纳入采集。等当前模型完成计算后读取，比较记录，变化时才保存。不要用公开隐藏区域事件代表所有折叠记录变化。
- 异步采集绑定编辑器模型、语言及正文版本；旧会话和旧版本结果不得覆盖新结果。输入法组合输入和恢复期间继续保护，结束后补采集被推迟的变化。
- 正常编辑期间及时写出；组件卸载和页面退出只作为补充。固定增加等待时间、仅增加关闭保存、删除 Monaco 校验值，都不能代替正确采集。
- 保留现有两个存储出口：单文档写旁路文档，分块写块清单。两者复用采集机制，避免只修一个入口。

当前证据不要求重写服务端。若后续目标包含正文与折叠的严格跨设备一致性，应另行定义正文版本关联、稳定位置标识、并发合并及确认协议。仅把同一份旧行号 JSON 搬进数据库字段，仍会复现本次问题。
