# 01：在折叠 Markdown 标题后回车创建同级标题

**What to build:**
在单文档模式和分块工作区中，用户于已折叠 Markdown 标题末尾按普通回车，可在整个折叠区之后继续编写同级标题，原内容保持折叠。

**Blocked by:** 无，可立即开始。

**Status:** ready-for-agent

- [x] 仅在 Markdown、单光标、无选区、光标位于已折叠标题行末且没有处于输入法组合期间时触发新行为。
- [x] 在当前折叠区的全部内容之后插入同级标题，沿用原来的标题级别，不复制标题文字；新标题标记后保留一个空格，光标停在该空格之后。
- [x] 原折叠内容保持隐藏，新标题可见；验证正文内容、实际隐藏范围与光标位置，不能只验证插入字符串。
- [x] 折叠区包含子标题时，插在全部子标题内容之后；文末和已有后继同级或更高级标题两种情况均正确处理，不修改既有正文。
- [x] 两种模式使用相同语义。其他语言、展开的标题、标题中间、多光标、选区、带其他修饰键的命令和输入法组合期间保持原有行为。
- [x] 输入法候选确认用的回车不额外创建标题，组合结束后的正常回车仍可触发。
- [x] 插入作为一次可撤销正文编辑，撤销与重做得到正确正文；另一客户端收到相同插入，现有协同机制继续工作。
- [x] 用项目测试覆盖可独立验证的边界，并用真实编辑器执行两种模式的上述场景；检查能在插入位置、级别、折叠或光标行为错误时失败。

### 2026-09-16 修复：折叠区间行号过期

用户报告：在折叠标题末尾回车生成的同级标题，被上一个同级标题的折叠收了进去。

根因是取折叠区间的来源。`headingEnterEdit` 原先读 `FoldingModel.regions`
的行号，而 monaco-editor
^0.52.2 把这份行号定格在上一次折叠计算上，每次内容变化只是把下一次计算推迟到防抖之后。于是从内容改动到下一次计算之间，读到的是旧行号。两种表现都已在真实编辑器复现：

- 折叠区上方插入一行后立刻回车：起始行对不上，规则不触发，默认回车把新行插进折叠区，折叠散开。
- 折叠区内部插入一行后立刻回车：结束行偏小，新同级标题落在上一个同级标题的折叠区里，正文中看不到它。

改为按区间对应的装饰读取行号，即 `src/markdownFolding.ts` 的
`collapsedRegionsOf`；`FoldingModel`
自己重算折叠时用的也是这份装饰，文本模型会随编辑移动它。

`scripts/headingEnter.browser.mjs`
增加 4 项检查（单文档与块编辑器各 2 项）：先压住 `triggerFoldingModelChanged`
制造确定的过期窗口，断言过期行号与实时行号确实不同，再检查正文、光标和新标题不落在隐藏区，放开折叠计算后隐藏区间正确。变异确认：把读取改回
`regions` 的静态行号，这 4 项失败，原有 38 项照常通过。

验证：`npm run check` 无错，`npm test` 217 项通过，`npm run test:browser`
115 项通过。

未验证：只覆盖了本地编辑造成的过期窗口。对端持续输入时折叠计算能被推迟多久，没有测量。

### 2026-09-16 修复二：文末插入后视图不显示新标题

用户报告修复一之后仍能复现。真实浏览器确认：文末场景下正文已经正确写入新标题，视图却不显示它。`ed.getModel().getLineCount()`
从 2 变成 3，`_getViewModel().getLineCount()` 仍然是 1，实际渲染只有一行。

原因是修复时机。文末插入落在折叠区最后一行的行尾，monaco-editor
^0.52.2会把折叠装饰和视图隐藏区一起撑大；`refreshEofFolding` 原本在
`executeEdits`
的光标回调里执行，也就是这次编辑仍在应用的过程中。视图模型随后按撑大的隐藏区重新推导行映射，把修复覆盖掉。改为在
`executeEdits`
返回之后再执行修复，五种形状（文末、文末空行、连续三节、非文末、嵌套）都恢复正常。

原有检查断言的是
`_getViewModel().getHiddenAreas()`。它由装饰支撑，此时读数正确，因此这组断言**不可能**在这个缺陷上失败。快照改为同时采集实际渲染的
`.view-line` 文本（trailing
space 渲染成不间断空格，读取时归一化），并在五个主场景断言完整可见行，在两个过期折叠场景断言新标题出现在视图里。变异确认：把修复移回光标回调，第一项检查即失败。

用户当时还看到不带 `##`
的一行出现折叠箭头。这一项未复现，也未定位，暂不认为已修复。

验证：`npm run check` 无错，`npm test` 217 项通过，`npm run test:browser`
115 项通过，`npm run build` 通过。

### 2026-09-16 修复三：普通行上多出折叠箭头

用户截图：`## 三、风险` 下面不带 `#` 的一行"测试"带着折叠箭头，刷新后仍在。

原因在保存折叠记录的一侧。在折叠标题行尾插入换行时，该折叠区的装饰整体下移一行，起点落到下一行；monaco-editor
^0.52.2 的 `FoldingRegions.sanitizeAndMerge`
把这种"已折叠但不再对应任何提供的区间"的跨度按 recovered保留下来。此时读到的 memento 就带着这条错位跨度，被写进共享清单，之后每次加载都恢复它，于是普通行永久带着折叠箭头。

`src/markdownFolding.ts` 新增
`keepHeadingFolds`：按当前正文重算标题折叠区间，只保留起点仍是折叠起点的跨度，在
`readFoldRecord` 与 `readFoldRecordSync`
两处保存路径上应用，语言不是 markdown 时原样返回。恢复路径不过滤，避免正文尚未加载时误删有效记录（票 09 仍未结）。已经存过错位跨度的文档，在该块下一次折叠或展开时自动写回干净记录。

`scripts/markdownFolding.test.ts`
增加 5 项：普通行跨度被丢弃、结束行过期仍保留、无正文的标题不成区间、代码围栏内的标题不成区间、非数组记录原样返回。`scripts/headingEnter.browser.mjs`
增加 1 项端到端检查：在块编辑器里种一条普通行跨度，折叠一个真标题触发保存，重开页面后只剩真标题那一条。变异确认：去掉过滤，该项报"a
folding arrow on a plain line survived into the saved record"。

验证：`npm run check` 无错，`npm test` 222 项通过，`npm run test:browser`
116 项通过，`npm run build` 通过。

### 2026-09-20 修复：标题中间换行生成普通行折叠

用户给出明确复现：折叠 `## 原折叠`，在末尾输入
`换行测试`，把光标移到“叠”和“换”之间后回车。正文应保持普通换行，不额外补
`##`，普通文字不应获得标题折叠功能。

真实浏览器复现补充了必要时序：输入追加文字后等待一次折叠重算，再回车。立即回车时未复现，等待 500 毫秒后能复现。Monaco
`0.52.2`
重算会把折叠位置标记的起点放到标题行末；标题中间换行把它移到下一行，后续计算把失去标题对应关系的已折叠范围标为自动恢复范围。于是原本不带标题标记的第二行出现折叠功能。

因果检查在没有 Rustpad 保存或恢复逻辑的独立 Monaco 编辑器中仍能复现，排除了旁路记录回传作为必要原因。只在换行前展开该标题，两种模式都不再产生错误范围。产品修复没有接管中间回车，而是在共同采集完成折叠计算后，定点移除 Markdown 中起点不属于有效标题的自动恢复范围。`source === 2`
表示自动恢复；`source === 1` 的显式手动折叠保持当前实时行为。

此处修复实时折叠模型，原有保存记录过滤继续保留。键盘和远端正文修改都经过同一处理，避免只处理某个按键入口。原有“标题行末生成同级标题”和“标题中间保持普通换行”语义不变。

新增 `scripts/foldMemory.browser.mjs`
在两种模式中验证：真实输入、等待重算、中间回车后正文精确一致、普通文字实际可见、全部范围均起于合法标题，以及撤销重做与远端修改。另验证显式手动折叠继续可用。修复前该场景因第二行存在自动恢复折叠而失败；修复后通过。

原 `scripts/headingEnter.browser.mjs`
的错误范围播种检查改为在同一次浏览器调用中立即记录播种结果。仍检查错误范围确实生成，并在后续重开后消失；不再要求新采集机制工作一段时间后错误范围仍存在。
