# 10：共享文档被迟到播种写成两份

**What to build:**
消除块清单与折叠旁路文档的"迟到播种"：一个客户端在自己认为文档还是空的时候插入整份内容，服务端把它变换后追加，文档于是同时存在两份，随后由某个客户端删掉重复的一半。本票交付修复与可复现证据。

**Blocked by:** 无，可立即开始。本缺陷早于 `.scratch/block-focus-and-folding/`
这一版工作，不由票 01 到 07 引入。

**Status:** ready-for-agent

## 证据

2026-09-15 用 `scripts/probe-manifest-doubling.mjs`
在同一个分块页面开三个浏览器上下文，服务端广播里出现：

```
LATE full-manifest inserts=1
  ["{\"version\":1,\"blocks\":[{\"id\":\"7lf6uv\",...,\"height\":200}],\"com…
operations containing a delete=1
  [117,-117]
```

同一探针在改动前的提交 `40fb8c3`
上给出同样结果（`[82,-82]`），因此这是既有缺陷。当前代码的操作数反而略少（6 对 8）。

`scripts/probe-folds-sidecar.mjs` 显示单文档模式的折叠旁路文档 `folds:<id>`
有同样问题，而且形态更危险：

```
["{}"]          ← 第一个客户端播种空折叠表
["{}",2]        ← 第二个客户端又播种一次，文档变成 {}{}
[2,-2]          ← 删掉重复的一半
[1,"\"markdown\":[…]",1]   ← 真正的折叠记录这时才写入
```

## 为什么危险

`applyFoldSidecarText`（`src/singleDocFolds.ts:254-277`）在首次初始化时采用任何**可解析**的旁路内容，包括
`{}`，并且**不与本地缓存合并**；只有内容无法解析时才回退到本地记录。刚被播种的旁路文档内容正好就是
`{}`。因此一个客户端完全可能把"什么都没折叠"当作权威记录采纳，丢掉本机原有的折叠。

翻倍期间文档内容形如 `{}{}`，这不是合法 JSON，`parseFoldMap`
会返回 null，于是又走本地兜底。采纳空记录、采纳本地记录还是采纳真实记录，取决于客户端在这段窗口里的到达时序。

- [ ] 找出提交 revision
      0 整份内容的代码路径，说明客户端为何在服务端已有内容时仍认为文档为空。块清单与折叠旁路文档都要覆盖，两者都走
      `RustpadHeadless.replaceContent`。
- [ ] 给出可复现的失败场景，证明修复前后行为不同。`scripts/probe-manifest-doubling.mjs`
      与 `scripts/probe-folds-sidecar.mjs` 是起点，可以整理成正式检查。
- [ ] 修复后，多个客户端同时首次打开同一页面不再产生迟到的整份插入，也不再产生修复用的删除操作。
- [ ] 折叠旁路文档不得出现内容为 `{}{}` 的中间状态。
- [ ] 重新审视"可解析即胜出、不与本地合并"这条规则：区分"确实没有折叠"与"尚未读到记录"。这条规则本身可能需要改，但不要在根因未明时先改它。
- [ ] 不扩大同步层对并发结构修改的保证，也不改动字符级 OT 的既有决策（见
      [ADR 0002](../../../docs/adr/0002-character-ot-for-structured-manifest.md)）。
- [ ] 修复不得改变块清单、折叠记录的存储格式，也不得影响票 01 到 07 的既有检查。
